Implementasi penuh blueprint (data fiktif)

Koreksi dari bagian sebelumnya: waktu digali lebih dalam ke interface asli dokumen Phase 9 (bukan cuma nama folder application/commands), ternyata QuestService resminya (§9.3.20) itu satu interface kohesif — startQuest, completeQuest, startObjective, completeObjective, semuanya balikin Result<T, SDKError> — bukan satu Command class terpisah per operasi seperti dugaan awal saya. Jadi versi penuh di bawah ini lebih akurat dari sketsa folder sebelumnya. Semua interface di bawah dikutip persis dari dokumen sumber; datanya (QX, "THE PLACEHOLDER") murni fiktif, bukan Q03.

core/ids, core/result, core/errors — dikutip persis dari dokumen

// core/ids/index.ts
export type QuestId = string & { readonly __brand: "QuestId" };
export type ObjectiveId = string & { readonly __brand: "ObjectiveId" };

export function questId(value: string): QuestId {
  return value as QuestId;
}
export function objectiveId(value: string): ObjectiveId {
  return value as ObjectiveId;
}

// core/result/index.ts
export type Result<T, E> =
  | { success: true; data: T }
  | { success: false; error: E };

// core/errors/index.ts
export type SDKErrorCode =
  | "NOT_FOUND" | "INVALID_STATE" | "INVALID_INPUT"
  | "PRECONDITION_FAILED" | "PERMISSION_DENIED"
  | "ALREADY_COMPLETED" | "ALREADY_EXISTS" | "NOT_AVAILABLE";

export interface SDKError {
  type: SDKErrorCode;
  message: string;
}

application/services/QuestService.ts — interface asli (§9.3.20) + implementasi fiktif

// interface-nya, dikutip persis — SATU service, bukan command per method
export interface QuestService {
  getQuest(id: QuestId): QuestState | undefined;
  getDefinition(id: QuestId): QuestDefinition | undefined;
  getActiveQuests(): readonly QuestState[];
  getAvailableQuests(): readonly QuestState[];
  startQuest(id: QuestId): Result<void, SDKError>;
  completeQuest(id: QuestId): Result<void, SDKError>;
  failQuest(id: QuestId): Result<void, SDKError>;
  startObjective(questId: QuestId, objectiveId: ObjectiveId): Result<void, SDKError>;
  completeObjective(questId: QuestId, objectiveId: ObjectiveId): Result<void, SDKError>;
}

// implementasi fiktif buat contoh — pola ini TIDAK ada di dokumen,
// tapi wajar diturunkan dari interface + EventBus di atas
class InMemoryQuestService implements QuestService {
  constructor(
    private readonly registry: QuestRegistry,
    private readonly eventBus: EventBus,
  ) {}

  completeQuest(id: QuestId): Result<void, SDKError> {
    const definition = this.registry.get(id);
    if (!definition) {
      return { success: false, error: { type: "NOT_FOUND", message: `Quest ${id} not found` } };
    }
    // ...validasi objective, update QuestState...
    this.eventBus.emit("quest.completed", { questId: id });
    return { success: true, data: undefined };
  }
  // getQuest / startQuest / startObjective / completeObjective: pola serupa
}

Hasilnya: begitu diimplementasikan penuh pakai interface asli (bukan cuma nama folder), bentuknya jauh lebih mirip arsitektur yang sekarang jalan daripada kesan "CQRS berat" di sketsa awal. Tapi tetap ada 3 biaya nyata yang tidak hilang: (1) content/ tetap tidak ada — folder quests/ tetap harus dikarang sendiri; (2) primitif inti (Result, SDKError, EventBus) harus dibangun dari nol — proyek sekarang sudah punya versi sendiri yang lebih ringkas (core/result.ts 13 baris, tanpa error-code enum terpisah); (3) EventBus generik seperti ini tidak pernah dipakai proyek sekarang — HackHub SDK sendiri sudah jadi event bus (Terminal.Command, Mail.Sent, dst.), jadi lapisan event bus buatan sendiri ini akan jadi lapisan ganda yang tidak perlu.

Rekomendasi

Pertahankan arsitektur yang sekarang jalan. Jangan migrasi ke blueprint asli.

  1. Sudah terbukti, bukan teori. Q01-Q03 FINAL LOCK di atas arsitektur ini, live-tested di HackHub sungguhan. Blueprint Phase 9 belum pernah dites sekali pun.
  2. content/ menutup lubang nyata yang blueprint asli tidak pernah selesaikan — cetak biru itu sama sekali tidak punya jawaban "data konkret satu quest taruh di mana", dan yang saya masukkan tadi (quests/) murni karangan saya sendiri buat mengisi lubang itu.
  3. Bukan CQRS seperti dugaan awal — tapi tetap dua lapis yang tidak perlu. Setelah dibangun penuh, QuestService asli ternyata satu interface kohesif, bukan command per operasi. Tapi blueprint tetap mewajibkan EventBus generik buatan sendiri, padahal HackHub SDK sendiri sudah berfungsi sebagai event bus (Terminal.Command, Mail.Sent, dst.) — jadi tetap dua lapis event system yang saling tumpang tindih, tanpa manfaat tambahan.
  4. Migrasi sekarang = biaya penuh, manfaat nol. Memindah 100+ file demi menyamai dokumen desain yang ditulis sebelum satu baris kode pun ada, sambil mempertaruhkan regresi ke 3 quest yang sudah lolos live-validation — tidak sepadan.
  5. Yang layak diambil dari blueprint sudah diambil. Domain modeling (quest, evidence, investigation, dst.) dan aturan kepemilikan state (StateStore tunggal, ConditionNode tunggal) itu justru inti benar dari Phase 9 — dan itu sudah diimplementasikan persis. Yang tidak cocok cuma mekanika file-layout dan lapisan event-bus generiknya, bukan filosofinya.
  6. Implementasi penuh (fiktif) mengonfirmasi, bukan membatalkan, kesimpulan ini. Membangun satu quest fiktif lewat interface asli dokumen — bukan cuma sketsa folder — tetap butuh 6 file baru (empat primitif core/, satu quests/qx/ karangan, satu adapter) untuk hasil yang secara perilaku setara dengan kode Q03 yang sudah ada. Detail berubah (bukan CQRS), rekomendasinya tidak.
