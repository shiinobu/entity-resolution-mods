# ENTITY RESOLUTION — Character & Email Contract

## Status

**ACTIVE CONTRACT — 2026-09-12** (revised 2026-09-14 — see "Revision history")

## Purpose

Character email addresses are canonical story identity. They must not be randomly generated at runtime.

## Rules

1. Every recurring character has one stable character ID, display name, and email address.
2. Character email addresses are defined in the content layer, not generated by `Random` APIs.
3. Fictional personal/individual character addresses (contacts not tied to a visible organization's own website, e.g. Adrian) use the `.void` domain.
4. Organization mailboxes use that organization's own hostname TLD instead — e.g. `@skynet-logistics.idx`, matching their `Website.Host` domain (`.idx` is the project's website TLD; see `docs/phase13-quest-structure-standard.md`). Never `.void` for an organization mailbox — `.void` is reserved for personal/individual contacts per rule 3.
5. Quest-critical mail must reference a canonical character email rather than an inline random address.
6. Quest-critical subjects and report bodies are canonical content constants so live validation is deterministic.
7. The player should not be required to invent or guess quest-critical recipient, subject, or report text.
8. Until a supported native draft/prefill API is verified in the HackHub runtime, the implementation must not invent a keyboard or mail-composer API. The current interim contract exposes the exact recipient, subject, and plain-text report template in the quest briefing and validates the sent message against the canonical contract.

## Revision history

- **2026-09-14**: Personal/individual character TLD changed `.lock` → `.void` (Adrian's own email domain, `entityresolution.lock`, read as a meta reference to the mod's own title — replaced with `phantom-net.void`, an in-fiction name with no such collision). Rule 4 rewritten: organization mailboxes were previously assumed to share the same fixed TLD as personal characters (originally `.lock`, with `@skynet-logistics.lock`/`@arka-systems.lock` given only as illustrative examples, never implemented) — corrected to instead follow that organization's own established website TLD (`.idx`), since an org's mail domain realistically matches its own web domain rather than a generic fictional-character TLD. This also surfaced two pre-existing flavor-text addresses on Q01's static pages that predated this contract and never matched either convention: `edge-gateway@skynet-logistics.idx` (already correct under the corrected rule 4 — left unchanged) and `security-review@skynet-logistics` (was missing its TLD entirely — fixed to `security-review@skynet-logistics.idx`).

## Future character additions

When Q02–Q16 introduce a recurring contact, add the identity to `src/content/characters.ts` before implementing the quest that sends or receives mail from that character.

Do not create per-quest random email aliases for recurring story characters.
